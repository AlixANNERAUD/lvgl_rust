# AGENTS.md

Guidance for coding agents working on this repository. `CLAUDE.md` and
`GEMINI.md` are symlinks to this file: edit `AGENTS.md` only.

## What this repository is

A Cargo workspace with three crates:

- `lvgl-rust-sys/` (package `lvgl-rust-sys`, crate `lvgl_rust_sys`): a `-sys` crate. It compiles
  [LVGL](https://github.com/lvgl/lvgl) from source with `cc`, generates raw
  `no_std` FFI bindings with bindgen, and exports the native build
  configuration to dependent build scripts. It exposes the C API as is.
- `lvgl-rust/`: the safe, `no_std` layer on top of it (in progress).
- `lvgl-rust-gen/`: the host-only generator used by `lvgl-rust`'s build
  script (in progress).

Downstream users run on microcontrollers (ESP32, ...) as well as native and
WebAssembly hosts. Existing users depend on `lvgl-rust-sys` through git (Cargo
finds the package by name inside the workspace; since the rename from
`lvgl_rust_sys`, such a dependency needs `package = "lvgl-rust-sys"` to keep
its key) and use `default-features = false`, `shadcn-theme`,
`color_depth_16`/`color_depth_32`, their own `lv_conf.h` and the legacy
`LVGL_FONTS_DIR` mode. Do not break these paths.

## Build model

`NativeConfig` in `build/main.rs` is the single source of truth. The same
include paths and definitions feed:

1. `cc` (the `liblvgl.a` archive, only with the `build-lvgl` feature);
2. bindgen (as `-I`/`-D` clang arguments);
3. the metadata exported through `links = "lvgl_rust_sys"`:
   `DEP_LVGL_RUST_SYS_INCLUDE_PATHS` (`;`-separated), `DEP_LVGL_RUST_SYS_DEFINES`
   (`;`-separated), `DEP_LVGL_RUST_SYS_CFLAGS` (`,`-separated `LVGL_CFLAGS`) and
   `DEP_LVGL_RUST_SYS_TARGET`. Two keys describe the build itself:
   `DEP_LVGL_RUST_SYS_BINDINGS` (absolute path to `bindings.rs`, read by the
   safe crate's generator) and `DEP_LVGL_RUST_SYS_LINKED` (`1` with
   `build-lvgl`, `0` otherwise).

Never add an include path or define to only one of these: the bindings, the
library and downstream C code (fonts) must agree on the ABI. The metadata names
and separators are a public contract used by dependent crates; changing them is
a breaking change.

Inputs:

| Input | Effect |
| --- | --- |
| `DEP_LV_CONFIG_PATH` | Directory containing `lv_conf.h` (required, except with `use-vendored-config` or `DOCS_RS`). Empty means unset. |
| `LVGL_CFLAGS` | Extra `NAME` / `NAME=VALUE` definitions, comma-separated. |
| `LVGL_FONTS_DIR` | Legacy mode: compile that directory's `.c` files into LVGL and bind its top-level headers. |
| `EMSDK` | Required for `*-emscripten` targets. |
| `color_depth_{1,8,16,24,32}` | Defines `LV_COLOR_FORMAT_DEFAULT` and `LV_COLOR_DEPTH`. Several enabled: smallest wins, with a warning. |
| `shadcn-theme` | Compiles and binds `lvgl_theme_shadcn`. |
| `build-lvgl` (default) | Compile the native library. Without it, only bindings are generated. |
| `use-string-functions` (default) | Link the Rust C string functions. |

Read every environment variable through `env_var()` in `build/main.rs`: it
emits `cargo:rerun-if-env-changed`. Variables that Cargo always sets (`TARGET`,
`OUT_DIR`, ...) go through `cargo_env()`. Any new input file or directory needs a
`rerun-if-changed`, otherwise edits will not trigger a rebuild.

Keep `build/config.rs` free of `cc`, `bindgen` and Cargo I/O so that
`tests/build_config.rs` can include it with `#[path]`. Put new parsing or
selection logic there, with tests.

## LVGL version

The `lvgl` submodule is pinned to **LVGL v9.6.0** (commit `80ca777e3`), the
latest stable release at the time of writing.

`git submodule status` and plain `git describe` show it as
`v9.3.0-1754-g80ca777e3`. This does **not** mean the checkout is outdated: the
upstream `v9.6.0` tag is lightweight and these commands only consider annotated
tags. Read the real version with:

- `git -C lvgl describe --tags` (prints `v9.6.0`);
- `lvgl/include/lvgl/lv_version.h` (`LVGL_VERSION_MAJOR/MINOR/PATCH`);
- the header of `lvgl/lv_conf_template.h`.

If `lvgl/` looks older than the commit recorded by the superproject (a `+` in
`git submodule status`), run `git submodule update --init --recursive` before
building: compiling old sources against the 9.6 `lv_conf.h` fails.

### Bumping LVGL

1. Check out the new release tag in `lvgl/` and stage the submodule.
2. Regenerate `conf/lv_conf.h` from `lvgl/lv_conf_template.h`. It must differ
   from the template only by:
   - `#if 1` instead of `#if 0` to enable the content;
   - `LV_COLOR_FORMAT_DEFAULT` wrapped in `#ifndef LV_COLOR_FORMAT_DEFAULT`, so
     the `color_depth_*` features can override it;
   - `LV_USE_ASSERT_NULL` and `LV_USE_ASSERT_MALLOC` set to `1`.

   Verify with `diff lvgl/lv_conf_template.h conf/lv_conf.h`. Then derive
   `lvgl-rust/conf/lv_conf.h` from it; the two differ only by
   `LV_USE_OBJ_ID 1` and `LV_USE_OBJ_ID_BUILTIN 0` (check with
   `diff lvgl-rust-sys/conf/lv_conf.h lvgl-rust/conf/lv_conf.h`).
3. Build and look for new LVGL deprecation warnings (`#warning ... is
   deprecated`). The build is expected to be warning-free with `conf/`.
4. Check the shims in `shims/` and the shadcn theme still compile, then run
   the full test suite.
5. Update the version in the README badge and feature list, in this file, and
   in the `vendored_lvgl_version_matches_readme` test in `src/lib.rs`.

## Testing

```sh
git submodule update --init --recursive
# Nested builds run offline; their packages have their own lockfile.
cargo fetch --manifest-path lvgl-rust-sys/examples/external-fonts/Cargo.toml
cargo fetch --manifest-path lvgl-rust-sys/tests/fixtures/font_incremental/Cargo.toml
cargo test -p lvgl-rust-sys -p lvgl-rust-gen               # full suite, a few minutes
cargo test -p lvgl-rust-sys --lib --test build_config      # fast loop, seconds
cargo test -p lvgl-rust-sys --lib --features shadcn-theme,color_depth_32
```

With [mise](https://mise.jdx.dev) installed, `mise install` sets up the
toolchain and `mise run fetch`, `mise run test`, `mise run test-fast`,
`mise run clippy`, `mise run fmt` and `mise run doc` wrap the same commands.
Cargo then goes through mbx ([mr boxington](https://github.com/jdx/mr-boxington)),
which caches the LVGL C objects and build script output; `mbx explain --last`
says why something was rebuilt. Keep `mise.toml` tasks and CI in sync.

`DEP_LV_CONFIG_PATH` defaults to `lvgl-rust-sys/conf/` through the root
`.cargo/config.toml` (only for
cargo commands run in this checkout; an explicit value wins).

`lvgl-rust` needs a configuration with the OBJ_ID hooks: it fails to build
against `lvgl-rust-sys/conf` (a `compile_error!` that says what to add). Test
it in a separate cargo invocation with its own configuration and target
directory, as its mise tasks do: `mise run clippy-safe`, `test-safe`,
`test-views-only` (no handles, `-sys` configuration, also with `defmt` and
`debug-counters`), `test-allocator`
(the `allocator` feature on a copy of the configuration with
`LV_STDLIB_CUSTOM`), `test-asan` (LVGL under
AddressSanitizer, with C library malloc so freed objects are visible),
`miri`, `loom`, `size-gate` and `test-compile-fail`. Do
not use `--workspace` for cargo commands that build `lvgl-rust`.

What the suites cover:

- `src/lib.rs` tests: LVGL initialization, color shims, the configured color
  depth really reaching the C library, the pinned LVGL version. Tests that touch
  LVGL global state must hold `lvgl_lock()`; LVGL is not thread safe and the
  test harness is multithreaded.
- `src/string_impl.rs` tests: C semantics of the string functions.
- `tests/build_config.rs`: `build/config.rs` logic, no cargo involved.
- Integration tests (`font_build_modes`, `incremental_font_build`,
  `native_build_interface`, `external_font_example`): build fixture packages
  with a nested `cargo --offline` through `tests/common::cargo()`, then inspect
  `bindings.rs`, `liblvgl.a`, binaries (`nm`, `objdump`) or Cargo's
  `Fresh`/`Compiling` lines. Each compiles LVGL, so they are slow.

- `lvgl-rust/src/tests.rs`: the core (sessions, handles, ownership, deferred
  requests, structural checks). The same tests run against LVGL and, under
  Miri, against `ffi_stub.rs`; keep the stub's behaviour in line with LVGL's
  for every function `ffi.rs` exposes. Tests hold the `LOCK` guard.
- `mise run miri` runs the core tests three times: without features, with
  `heap` (the deferred-free list and `LvBox` against the stub's heap,
  `ffi::malloc`/`free`, where Miri's leak check catches a block never
  freed), and with `growable-registry` (registry chunks from the global
  allocator; reachable from the static, so not reported as leaks).
- `lvgl-rust/src/tests.rs` `protocol` module: loom models of `Owned::drop`
  racing the drain (`--cfg loom`), and with `growable-registry` racing the
  publication of a chunk (`mise run loom` runs both).
- `lvgl-rust/src/tests.rs` `growth` module (`growable-registry`): chunk
  arithmetic up to the 65,535-slot limit, then objects filling the static
  slots and several chunks. `test-safe` runs with and without the
  feature (`defmt` and `debug-counters` in both). Tests
  that fill the registry must stop at `reg().capacity()` with the
  feature (the 65,535-slot limit is out of reach of LVGL's heap).
- `lvgl-rust/tests/lifecycle.rs`: `init`, ticks, `deinit` (terminal, so in
  its own process).
- `lvgl-rust/tests/compile_fail.rs`: trybuild cases
  (`tests/compile-fail/**/*.rs`, with `async/` and `heap/` for those
  features) that must fail to build, each with its expected `.stderr`: views
  used across exclusive calls or past their session, two `ObjMut`, a
  created child used with exclusive calls or alongside its parent's
  `ObjMut`, an `ObjMut` kept after `into_base`, `!Send`
  values crossing threads or given to `on`/`timer`/`post`, capturing
  closures (post-monomorphization `const` asserts: trybuild builds to
  codegen, so they are caught), exclusive calls from handlers, event
  codes sent without the access they need, `Owned`,
  `Handle` and `StaticRx` misuse, non-`'static` retained data. Ignored by
  plain `cargo test` (rustc's messages change between versions); `mise run
  test-compile-fail` runs it on a pinned compiler. When raising that
  version, or after changing a message the cases hit, refresh the snapshots
  with `TRYBUILD=overwrite mise run test-compile-fail` and check that every
  case still fails for its stated reason. A new soundness guarantee
  enforced by types gets a case here.
- `lvgl-rust/size-gate/gate.sh`: links firmware for thumbv6m and riscv32imc
  (16 slots and views-only) and checks the crate's symbols: registry size and
  `.bss` placement, no `.data`, no `core::fmt` or panic code, the OBJ_ID
  hooks, and a code budget per target (set in the `size-gate` task). Raise a
  budget only in the change that needs it, and say why. The task also
  checks that `async` and `heap` compile for both targets, and
  `test-views-only` runs with and without them. An optional fourth
  argument enables firmware features (`defmt`, `debug-counters`,
  `growable-registry`); the gate then expects the 8 bytes of counters in
  `.bss`, and none without `debug-counters`, and with `growable-registry`
  `4·(16 − log2 N) + 8` more bytes of registry. That firmware brings a
  bump allocator over a 4 KiB static (its own symbols, not the crate's),
  and its runs have their own budgets.
- `lvgl-rust/tests/counters.rs`: the `debug-counters` values (drained and
  refused requests, skipped callbacks, leaked drivers) and, with `defmt`,
  which types implement `defmt::Format` (a host has no logger).
- `lvgl-rust/benches/overhead.rs` and `mise run overhead`: times each
  safe operation against the raw call it replaces (release profile,
  feature `heap`, `lvgl-rust/conf`, safe and raw samples alternating),
  then runs the size gate and writes `documentation/reference/overhead.md`
  with the machine, compiler, LVGL version and commit. Not in CI: host
  times vary between machines. Without the thumbv6m or riscv32imc C
  toolchains the script takes the crate's sizes from the size-gate job of
  CI, and the page says so. That page is generated: never edit it by
  hand. Rerun the task, on a clean commit, when a change moves the
  numbers (the core, the trampolines, the registry, a size budget), and
  update the figures other pages quote from it.

Rules for integration tests:

- Always start nested builds with `common::cargo()`. It sets `--offline`,
  `CARGO_TERM_COLOR=never` (CI forces colors, which breaks matching on
  `Fresh lvgl-rust-sys`), the vendored config, and clears `LVGL_FONTS_DIR` and
  `LVGL_CFLAGS` inherited from the outer environment.
- Use `common::scratch_dir()` for fixtures and separate target directories, and
  remove them at the end of the test.
- A fixture with its own `Cargo.lock` needs an empty `[workspace]` table (so
  Cargo does not attach it to the root workspace) and a matching `cargo fetch` in the
  `fetch` task of `mise.toml` (which CI runs), otherwise CI fails with "no
  matching package".
- Restore any tracked file a test modifies, even on failure (see `RestoreFile`
  in `tests/incremental_font_build.rs`).

## Generated wrappers

`lvgl-rust/build.rs` runs `lvgl-rust-gen` on the bindings of the current
build (`DEP_LVGL_RUST_SYS_BINDINGS`) and writes `$OUT_DIR/gen.rs`, included
as the `widgets`, `enums`, `functions` and `props` modules, plus `$OUT_DIR/coverage.txt`
listing what happened to every bound function. Disabled widgets are simply
absent from the bindings, so nothing is generated for them; `lv_use_<x>`
cfgs mirror the `LV_USE_*` values for hand-written code.

- **A function is wrapped only if `access.toml` lists it**, as `shared`
  (view method), `exclusive` (`ObjMut` method, or `&mut Lvgl`), `pure`/`isr`
  (free function) or `raw` (stays in `sys`). `access.toml` is generated by
  the audit (below): never edit it by hand.
- Pointer parameters are retained (raw) until `overrides/` classifies them
  (`copied_str`, `static_str`, `copied`, ...). `@nullable` in the header gives
  `Option`. Object returns are untyped (`&Obj`) unless an override certifies
  the class.
- Styles and fonts are typed by the generator, without overrides:
  `lv_style_<x>(lv_style_t *, ...)` becomes a `StyleMut` method (exclusive
  whatever the audit says, since objects may be reading the style),
  `const lv_style_t *` parameters take a `'static` `Style` or `ConstStyle`
  (`StyleRef`), `const lv_font_t *` ones a `&'static Font`, and
  `lv_style_selector_t` a `Selector`. `lv_font_t *` (writable) stays raw:
  fonts may sit in flash. Each `lv_style_set_<p>` whose value fits a
  constant also gets a `props::<p>` constructor for `const_style!`, and
  each `lv_font_t` static of the bindings a `const` `Font` constructor.
- Data LVGL keeps and reads later (image sources, button maps, gradients,
  transitions, color filters, color keys) is mapped with
  `kind = "retained", rust = "<Type>"` to a type of `lvgl-rust` that makes
  it `'static` and checks its layout (terminators, sizes, first bytes):
  `RETAINED_TYPES` in `tables.rs` lists them, each with a `const fn
  as_ptr`. Data LVGL writes stays raw. Retained data whose setter needs
  more than a type is wrapped by hand: keyboard layouts (`KeyboardMap`,
  global per mode, with `set_popovers` showing the mode's layout again
  before LVGL copies its control map), scale labels (`ScaleLabels`; the
  15-bit tick counts keep LVGL's `uint16_t` label index from wrapping) and
  grid templates (`grid.rs`: the grid layout is set only with both
  templates, in the local style, the other layout setters refuse
  `LV_LAYOUT_GRID` and `remove_local_style_prop` the templates, so LVGL's
  unchecked subgrid path, `lv_grid.c:321-325`, is unreachable; cell spans
  are bounded because LVGL's clamp overflows, `lv_grid.c:550-558`). The
  template style setters stay raw: they accept NULL, which would hide the
  local templates.
- A string getter that points into the object stays raw until an override
  says `returns = "borrowed_internal"` (after checking that the pointer is
  the object's own text, a literal or static text it was given, never
  something else such as an image source). It becomes a copy-out
  `x_into(&self, buf)` on the view, since a shared setter could free the
  string, and a borrowing `x(&mut self)` on `ObjMut`.
- `classes.toml` `crate_owned` functions can never be shared or exclusive;
  `manual` ones are wrapped by hand in `lvgl-rust/src/base/` or next to
  the types they need (`manual.rs`, `grid.rs`, `button_map.rs`;
  `chart.rs`: series tokens checked against the chart's list; `table.rs`:
  cell bounds and sizes; `tileview.rs`: tiles and a size check wrapped
  around LVGL's scroll handler by `create`; `calendar.rs`).
- `classes.toml` `[composite.<widget>]` tables drive the structural checks:
  `parts` are the objects LVGL holds pointers to (getters, `child:N`,
  `shim:`), `indexed` how many levels below a part LVGL finds objects by
  index, and `parts = []` declares a widget whose children are all the
  application's. `closed = true` marks a widget that finds or casts its
  children by position (a roller's label, a tile view's tiles): no child
  is created in it, moved into it or reordered within it except through
  its own API (`child:N` parts need it). `pinned = true` marks a widget
  whose handlers read its parent as the widget that created it (calendar
  headers): it never changes parent. Inside a widget class with no entry,
  nothing can be deleted, owned, moved, reordered or cleaned, and no child
  can be created. Subclasses inherit their base's entry
  (`lv_obj_has_class`). Add an entry only after reading the widget's
  sources (constructor, cached pointers, `lv_obj_get_child` uses, handlers
  that walk up to a parent).
- Pointer parameters stay raw, and index parameters (`idx`, `*_id`, `row`,
  `sel_opt`, ...) too, until an override gives their kind with a `why`
  citing the lines that copy, write or bounds-check them (a check under
  `LV_USE_CHECK_ARG` or `LV_ASSERT` does not count: configurations turn
  them off). Functions in `relations.toml` are raw unless wrapped by hand
  with a clear-on-delete watcher (`manual.rs`: the keyboard's textarea);
  `raw = true` marks those that cache another object and cannot be cleared.
- An exclusive call taking another object takes a `Handle` (resolved
  under the exclusive access) and returns a `Result`; one returning an
  object lends a view borrowing the `ObjMut`.
- `lv_<w>_create` follows its `access.toml` entry like any other call
  (every widget's is exclusive: creation adds the object to the default
  group, which can focus another object whose handler moves objects). An
  exclusive one becomes `W::create(&mut ObjMut<'_, P>) -> &W`, a view
  borrowing the parent's `ObjMut` (never an `ObjMut` of the child: its
  exclusive calls could delete the parent while the parent's `ObjMut` is
  in scope), and `create_owned` with the same parent; a shared one would
  take a parent view, and one that `consumes` (may delete its parent)
  stays raw. No API derives an `ObjMut` from another one by
  reborrowing (`into_base` takes `self`): a consuming call on the
  reborrow could delete the original's object. The hand-written
  `Obj::create` and `Lvgl::create_screen` follow `lv_obj_create`'s entry.
- `events.toml` (generated by the audit, below) gives `HANDLER_SHARED`,
  the bitmask `handler_allowed` (`event.rs`) tests, and the code types
  `SafeEventCode` (sendable with shared access: `Obj::send_event`) and
  `SendableEventCode` (deleting codes too: `ObjMut::send_event`, which
  consumes the access and returns it if the object survived), plus
  `HANDLER_RESTRICTED` (`query_handler_allowed`, `query.rs`) and
  `QueryCode`, the codes restricted handlers (`Obj::on_query`) take.
  None has a public constructor.
- Table errors always fail the build. Entries for functions missing from a
  build's bindings warn (they may be disabled by that `lv_conf.h`) unless
  `universe.txt` lists them; `LVGL_RUST_GEN_STRICT=1`, set for every mise
  task, turns those warnings into errors.
- After changing the generator, rerun `UPDATE_GOLDEN=1 cargo test -p
  lvgl-rust-gen` and review the diff of `tests/golden/`.
- On an LVGL bump, add `tables/lvgl-<major>.<minor>/`: the generator refuses
  bindings without matching tables. Then run `mise run bump`: it rewrites
  `universe.txt` from the bindings built with `lvgl-rust/conf` and lists
  `[hierarchy]` lines that disagree with the `.base_class` of the LVGL
  sources, and stale table entries (functions or parameters that no
  longer exist). Fix those by hand, then run `mise run audit`.
  `audit-check` runs `bump --check`.

## Access audit

`mise run audit` (`lvgl-rust-gen audit`, feature `cli`) compiles the vendored
LVGL with `lvgl-rust/conf` to LLVM IR (pinned clang from mise, fixed
`x86_64-unknown-none-elf` target, so the result does not depend on the
host), builds a call graph and rewrites `access.toml` and `events.toml`;
CI runs `mise run audit-check`. A function that can reach a sink (`sinks`
in `audit.toml`: deleting objects or displays, shrinking children arrays,
freeing group nodes) is exclusive, with the witness path as `why`; one that
schedules a deletion for later is raw; anything else is shared, unless the
held-region analysis (below) makes it exclusive.

The graph is conservative; `audit.toml` makes it precise without losing
soundness:

- callbacks are tracked per struct field (`_lv_obj_class_t.3`, ...), through
  setters' parameters; an indirect call reaches only what LVGL stores in
  that field, and an unresolved one every escaping function of its
  signature;
- event sends with constant codes reach only the handlers of that code, and
  `if (code == ...)` guards in handlers are followed;
- widget code reaches only handlers registered by core code, by itself, by
  widgets it creates or that create it, and by its `peers`;
- animation callbacks are attributed to whoever installs them
  (`caller_slots`);
- animations are told apart (`[animation]`, `identity.rs`): each local
  `lv_anim_t` a function fills through setters and starts is a profile
  (its callbacks per field, the struct type of its `var`, whether
  `early_apply` is off); a local whose address goes anywhere else matches
  everything. `lv_anim_delete(var, exec_cb)` and the replacement in
  `lv_anim_start` are specialised per key (a constant `exec_cb`, the type
  of `var`) and reach only the `deleted_cb`s of the animations the key can
  match. Pointer types come from uses (`getelementptr`, forwarding to a
  typed parameter), generalised to the root of the first-member chain
  (`_lv_label_t` is `_lv_obj_t`); two roots differ only if neither starts
  with a union or byte buffer. The held-region analysis uses the same keys:
  the animation `lv_anim_start` keeps across its callbacks is freed only by
  removals that match it, across the codes its callbacks send; the one
  `remove_concurrent_anims` compares against (`concurrent_removal`) only
  across the codes of the `deleted_cb`s of animations the removal matches
  (they share its `exec_cb` and `var`); and an animation the frame itself
  unlinked from the running list (`unlink`: a must analysis over the
  blocks, the local not written since and its address never stored or
  passed to a call) by no other removal, since every
  removal frees only what it finds in that list;
- object creation is specialised by class (`[construction]`): an
  `lv_obj_class_init_obj(obj)` call whose argument is a local holding only
  the result of `lv_obj_class_create_obj(&class, ...)`, with no call and
  no store through a pointer on any path between them, runs only the
  constructors of that class and its bases (read from the class globals'
  initializers);
- `[infeasible.<name>]` removes calls that cannot happen in one calling
  context (`context = "caller -> callee"`, `calls`), with the LVGL lines
  that prove it: the callee is specialised for that caller;
- `[own_deletions.<function>]` lists direct deleting calls that delete
  only an object the function just created (`lv_msgbox_create` deleting
  its new box when the content allocation fails), with the lines that
  prove it: `consumes` is computed without those edges, the function
  stays exclusive, and any other deleting path still makes it consume;
- `exceptions` holds hand decisions (pure functions), with a reason.

### Event codes (`events.toml`)

One `[code.LV_EVENT_X]` per code of `lv_event_code_t` in this
configuration (names and values come from clang: an AST dump filtered on
`LV_EVENT_`, then a generated C file compiled to IR, so `#if` conditions
and implicit values are exactly LVGL's; custom codes, flags and sentinels
are left out):

- `deleting`: a handler of the code (or of every code), or a class event
  callback sending it runs, reaches a sink;
- `param`: the `param_getters` (`lv_event_get_param` and getters that
  return or dereference the parameter unchecked; `param_checked_getters`
  return 0 for NULL) that code running for it calls under a guard that
  admits it;
- `sendable`: `"no"` if `param` is not empty (safe code sends NULL),
  `"exclusive"` if `deleting` or if the send frees memory held across a
  shared code, else `"shared"`;
- `handler`: `[event_policy]` hand decisions first (`"none"` for display
  codes and `CREATE`, with a `why`; `sendable = "no"` for `DELETE`), then
  `"restricted"` for `blockable_codes` (draw and query codes: handlers
  there would run in the middle of layout or rendering; their handlers
  get a `QueryEvent`, which reaches only the typed parameter), else
  `"shared"`. A shared code becomes restricted only if a hazard cannot be
  resolved by making its freer exclusive (a freer with a hand-fixed
  access): the audit warns.

### Held-region analysis (`held.rs`)

A handler runs inside the frame that sent its event, with shared access.
It is sound only if no frame keeps a pointer into memory a shared function
can free and uses it after the send. At `-O0` every C local is an
`alloca`, so a frame *holds* region R across call site C when a local that
received a pointer into R (or a struct copy, `llvm.memcpy`, containing
one) is read after C and C can send events. Regions are `Obj(T)` (an
object of struct type T, matched by type), `Buf(path)` (the buffer whose
pointer is at an embedded field path, matched by path suffix, so one
`lv_array_t` is not every `lv_array_t`) and `Copy(path/*)` (every buffer
under a copied struct). Per function the audit computes, to a fixpoint
over calls, indirect calls and sends (following the event code): the
regions `free_primitives` can release (instantiated with each call's
arguments), the codes each call site can send, and its holds (a callee's
holds of its parameters are charged to it with the caller's region). A
hazard is a hold of R across a code whose handlers would be shared, and a
shared function whose frees contain R. Each hazard is decided in order:

1. a `[guarded.<name>]` entry covers it (`regions`, `*` globbing, and at
   least one of `freers`, `holders` or `via`, a function the free's
   witness chain must name) with the runtime check and its reason: LVGL's
   own flags (`anim_list_changed`, `timer_deleted`, `is_traversing`) or
   the crate's (`lvgl_sys_obj_events_traversing` for H1);
2. every hazardous code is in `blockable_codes`: they stay restricted and
   the freer stays shared;
3. otherwise the freer becomes exclusive, with `why = "frees <R>, held by
   <frame> keeps <local> across <call> (... frees <R> in <primitive> for
   <callers>) (codes ...)"`.

Fresh memory (results of `alloc_primitives` and of functions returning
only such memory) freed before the function publishes it (stores it or
passes it to a callee that keeps it) is not a hazard; `[unpublished]`
lists functions whose frees happen only on paths where the publication
failed, with a reason.

`mise run audit -- --verbose` prints, besides the handlers and class
callbacks that reach a sink, every hazard (marked when guarded) and two
review lists that are never auto-decided: **aliases** (a field that stores
a pointer to a buffer owned by another field, `lv_dropdown_open`'s list
label, and the shared freers of that buffer that do not update it) and
**free without clear** (frees of memory a global names with no later
store to it; the audit fails if such a function is shared and not
crate-owned). It also prints where precision stops, never counted as
safe: unknown holds (pointers with no known origin or type: unresolved
call results, `phi`s, values that go through heap memory), shared freers
of memory of unknown origin. Limits of the model: holds are computed
without the code dispatched in the holding frame and per local (not per
path), stale indices (a table `row` after a send) and pointers two levels
inside a copied struct are not tracked, publication is ordered by
instruction, not by path, and only object events are modelled for
`sendable` (display and input-device events reach their own handlers).

Change `audit.toml` only with a source-backed reason in a comment, and
review the `access.toml` and `events.toml` diffs.

## Pitfalls

- **Shared versus exclusive in `lvgl-rust`.** A view (`&Obj`) borrows
  `&Lvgl`; any call that may free an object, start deleting one, shrink a
  children array or free memory LVGL objects point to must take `&mut Lvgl`
  or an `ObjMut`, never `&self` on a view. Deletions requested from shared
  code go through the registry (`delete_later`, `Owned::drop`) and run in the
  drain.
- **Event handlers.** Rust handlers run inside the LVGL frame that sent the
  event, with shared access. `handler_allowed` (`event.rs`) tests the
  generated `HANDLER_SHARED` mask (`events.toml`): only codes whose send
  sites hold no memory a shared call could free. In callbacks, registering
  on an object LVGL is sending to is refused
  (`lvgl_sys_obj_events_traversing`, the `[guarded.event_list_add_obj]`
  entry of `audit.toml`), and views and handles of objects under a
  deleting ancestor are refused (`in_deletion`). Restricted handlers
  (`query.rs`) get a `QueryEvent`: no `Lvgl` access, no views, only the
  code's parameter, read and written in place. Give it only accessors
  whose every value is valid for LVGL (colors, opacities, the answer of
  a query); sizes, radii, pointers and drawing stay raw. Never add a way
  to get a `'static` `Lvgl` or view (a `DepthGuard` or session that can be
  leaked safely): a thread-local would carry it into restricted handlers,
  which is why `LvglAccess` forbids `'static` guards. Change the tiers
  through `audit.toml` and `mise run audit`, never by hand.
- **Registry atomics.** No read-modify-write anywhere (thumbv6m and
  riscv32imc have no compare-and-swap): code without a token only stores
  `req`, `any_req` and `ticks`. `Registry::request_drop` and `drain` pair
  SeqCst fences; keep that pairing if either side changes, and rerun
  `mise run loom`. With `growable-registry` (cfg `lvgl_rust_growable`),
  a chunk is initialized before its pointer is stored with Release, once,
  by the token holder; every lookup loads it with Acquire. Chunks never
  move and are never freed (an `Owned` may store into its slot after
  `deinit`), and every index lookup stays panic-free (indices of no
  published chunk give the FREE sentinel slot).
- **Display buffers.** LVGL checks draw buffer sizes only when they are
  set (and only with `LV_USE_CHECK_ARG`). A display call that changes what
  is rendered into them (resolution, rotation, color format, render mode)
  goes through `Display::change_geometry` (`display.rs`): `Geometry::fits`
  mirrors `lv_refr.c` and `_calculate_draw_buf_size`, and
  `lvgl_sys_display_reshape_buffers` gives every buffer the new shape,
  since direct mode with two buffers copies areas between them with their
  stored shapes. Drivers sit right after their header (`layout::trailing`)
  in a `repr(C)` cell or an `LvBox` block; keep both layouts in step.
- **Diagnostic counters.** `counters::count` is the only way to bump
  them, a load and a store like the registry (no read-modify-write), and
  it compiles to nothing without `debug-counters`. Count only what the
  crate does or refuses silently: an error returned to the caller needs no
  counter.
- **New LVGL calls in the core** go through `base/ffi.rs`, with a matching
  model in `base/ffi_stub.rs`, or Miri cannot run the tests.
- **Bindgen output lints.** Generated code lives in the `bindings` module in
  `src/lib.rs`, which carries its own `#[allow(...)]` list. Do not add
  crate-wide allows for bindgen warnings.
- **`c_char` signedness.** `c_char` is `i8` on x86 and `u8` on aarch64 and some
  embedded targets. Code like `x as u8` can look redundant to clippy on one
  host and be required on another; allow `clippy::unnecessary_cast` locally
  with a comment rather than removing the cast.
- **C semantics in `string_impl.rs`.** These functions replace libc for LVGL:
  compare bytes as `unsigned char`, never read past `n`, and treat the NUL
  terminator as part of the string for `strchr`/`strrchr`. Add a test for any
  change.
- **Color depth in `lv_conf.h`.** LVGL 9 configures `LV_COLOR_FORMAT_DEFAULT`;
  `LV_COLOR_DEPTH` is derived from it and deprecated. A config that hard-codes
  either value without `#ifndef` silently conflicts with the `color_depth_*`
  features.
- **Fonts.** The recommended mode builds fonts in a separate crate from the
  exported metadata, so font edits never rebuild LVGL. Legacy `LVGL_FONTS_DIR`
  must keep working, but must stay opt-in: never scan the working directory
  for fonts implicitly.
- **Cross-compilation.** The build script never passes `--target` to clang:
  for non-host targets bindgen derives the clang triple from `TARGET` itself
  (`riscv32imc-unknown-none-elf` becomes `riscv32-unknown-none-elf`, `espidf`
  becomes `elf`, `aarch64-apple-*` becomes `arm64-apple-*`). The C compiler
  comes from `cc`, which honours `CC_<target>`/`CFLAGS_<target>`; give bindgen
  the same headers with `BINDGEN_EXTRA_CLANG_ARGS_<target>` (see the
  `cross-riscv32` task). Targets without a C library (`wasm*-unknown-unknown`)
  get `shims/freestanding/` on every include path, for `inttypes.h`.
  `wasm32-wasip1` uses wasi-sdk (`CC_wasm32_wasip1=wasm32-wasip1-clang`,
  bindgen gets `--sysroot`); WASI has no threads and wasm aborts on panic,
  so tests that spawn threads or catch panics carry
  `cfg_attr(target_os = "wasi", ignore)` or
  `cfg_attr(panic = "abort", ignore)`: keep the ignored part in a test of
  its own so the rest still runs there. The root `[env]` of `mise.toml`
  points `cc` and bindgen at the Debian/Ubuntu riscv32 and arm-none-eabi
  toolchains. CI builds `wasm32-unknown-unknown`,
  `riscv32imc-unknown-none-elf` (the riscv C toolchain is declared in
  `[bootstrap.packages]` of `mise.toml`, installed with
  `mise bootstrap packages apply`) and `wasm32-wasip1` (wasi-sdk and
  wasmtime are tools of the `cross-wasip1` task, no bootstrap packages),
  and runs the wasip1 tests under wasmtime; host builds do
  not prove that a change works on other targets (xtensa included), so say
  what you actually checked.
- **Submodules.** Never edit files under `lvgl/` or `lvgl_theme_shadcn/`. Fix
  problems in `build/`, `shims/` or `conf/`, or bump the pinned commit.
- **Generated files.** `bindings.rs` and `liblvgl.a` live in `target/`; never
  commit build output. The `*.generated.c` font fixtures are small hand-written
  stand-ins for `lv_font_conv` output.

## Documentation

User documentation lives in `documentation/` and follows
[Diátaxis](https://diataxis.fr); `documentation/README.md` is the index.

- `tutorials/`: lessons followed from start to finish
  (`first-application.md`, whose program is
  `lvgl-rust/examples/first_application.rs`: keep the two in step).
- `how-to-guides/`: one goal each, in steps, with pitfalls.
- `explanation/`: why the crate works the way it does.
- `reference/`: every item, input and number, to look up.
  `reference/overhead.md` is generated by `mise run overhead`.

Rules:

- Use full words in file and directory names (`documentation`,
  `how-to-guides`, `configuration`), never shortened forms, and link
  between pages with relative paths. Add new pages to the index and to the
  Documentation table of the root `README.md`.
- Check every API name, signature, size and default against the source
  and the generated `gen.rs`. Quote time and memory figures only from
  `reference/overhead.md`, with a link to it.
- Describe users generically ("an embedded OS", "your application").
- When a user-visible change lands, update: `reference/api-overview.md`
  (public items), `reference/features.md` (Cargo features),
  `reference/build-configuration.md` (environment variables, metadata,
  cfgs, generated files), `reference/errors.md` (`Error` variants or the
  functions returning them), `reference/supported-targets.md` and
  `how-to-guides/build-for-embedded-targets.md` (targets and CI jobs),
  `reference/development-tasks.md` (mise tasks and workflows), the
  explanation page of the mechanism it changes (access, lifetime, events,
  generator), and the how-to guide a user would follow.

## Conventions

- Rust 2024 edition, MSRV 1.89 (`rust-version` in the root `Cargo.toml`).
  Format with `cargo fmt`; match the surrounding style and comment density.
- Commit messages follow `type: summary` (`build:`, `conf:`, `fix:`, `test:`,
  `docs:`, `ci:`, `feat:`), with a body explaining the why for anything
  non-trivial.
- Keep pull requests focused, one concern each. For larger work, prefer a
  stack of small PRs, each targeting the previous branch.
- Do not add AI attribution (no `Co-Authored-By` trailers for assistants and
  no "generated with" lines in commits or pull requests).
- Document user-visible changes (features, environment variables, metadata) in
  `documentation/` (see Documentation) and the READMEs, and keep this file up
  to date when the workflow changes.
